# Перемер записи (`dumps`) после смены формата float — 30 октября 2026

**Итог.**
- **Память.** Смена формата float в коммите `a3697b3` не изменила память записи ни на Windows, ни на Linux.
- **Скорость на Linux.** Она тоже не изменилась.
- **Скорость на Windows.** Запись `canada.json` стала медленнее на 8–9%. Причина — раскладка кода у gcc 15, а не новый формат.
- **Исправление.** Оно внесено следующим коммитом: функция записи экспоненты больше не встраивается. С ним скорость записи на обеих машинах равна старой версии, см. [итоговую проверку](#итоговая-проверка-исправления).

## Что сравнивали

Обе версии собраны в один день на одной машине одним компилятором и мерились одними и теми же скриптами.

- **Старая версия.** Исходники коммита `d744abe` — те же, на которых сняты результаты 29 октября.
- **Новая версия.** Исходники `a3697b3`, в котором float пишется в формате orjson.

| | Windows | Linux (farmgpu) |
|---|---|---|
| Процессор | AMD Ryzen 9 5900X | Intel Core i3-13100, 8 потоков |
| ОС | Windows 11, 10.0.26300 | Ubuntu, ядро 6.8, glibc 2.39 |
| Python | CPython 3.11.4 | CPython 3.12.3 |
| Компилятор | gcc 15.1.0 (MinGW-W64), NASM 2.16.03 | gcc 13.3.0, NASM 2.16.01 |
| orjson | 3.13.0 | 3.13.0 |
| SHA-256 oxjson, старая / новая | `dc7fb0bd…` / `ac6ac303…` | `6ee70a0a…` / `b4751175…` |
| Метрика памяти | private commit | RSS |

Бинарник старой версии на Windows по хешу не совпадает с бинарником 29 октября (`509f71bb…`), хотя исходники те же. Поэтому старую версию сравнивали в пересборке, а не по цифрам 29 октября.

Как мерили, скрипт — [run.sh](run.sh):
- **Скорость.** `bench/current_compare.py --repeats 7`: семь документов, по 7 свежих процессов на библиотеку и документ. Серии идут в порядке старая → новая → старая → новая, всего четыре серии на машину. GC включён.
- **Память.** `bench/memory_audit.py --operations dumps --repeats 5 --rounds 10 --calls 20 --retain 6`: семь документов, обе библиотеки, по 5 свежих процессов на сочетание — 140 процессов на машину.
- **Время.** Windows — 14:29–14:35 UTC, Linux — 14:29–14:32 UTC. Ошибок нет.
- **Проверки.** До замеров `tests/check_dumps_orjson.py` и `tests/check_dumps.py` прошли на новой версии на обеих машинах, на AVX2 и на переносимом пути. Расхождений с orjson ноль, в том числе на 57 613 объектах с текстом float.

### Попарная проверка

Чтобы отделить замедление от шума, сделали A/B-замер скриптом [ab.py](ab.py):
- каждый замер — свежий процесс;
- старая и новая версии чередуются, 15 пар на документ;
- в каждом процессе 10 вызовов прогрева, затем медиана 60 вызовов.

| Машина | Документ | новая / старая | пар, где новая быстрее |
|---|---|---:|---:|
| Windows | `canada.json` | 1,086 | 1 из 15 |
| Windows | `twitter.json` | 1,007 | 7 из 15 |
| Windows | `numbers.json` | 1,215 | 6 из 15 |
| Windows | `marine_ik.json` | 0,993 | 5 из 15 |
| Linux | `large_50k.json` | 1,002 | 7 из 15 |

Замедление `canada.json` на Windows подтвердилось. По `twitter.json` и `marine_ik.json` разницы нет. По `numbers.json` вывода нет: медиана сдвинулась, но выигрыши разделились почти поровну. Это следствие тех же двух уровней времени.

### Причина замедления canada на Windows

В `canada.json` нет ни одного числа, которого касается новый формат: все числа пишутся в десятичной форме без экспоненты. Изменилась сама функция записи экспоненты `jf64_exp`: в ней появилась ветка для отрицательных экспонент меньше 10. Эта функция встраивается в каждое место записи float. После изменения `rec_list` выросла с 1089 до 1110 инструкций, `rec_value` — с 1531 до 1554 (объектный файл `json_dumps_walk.o`, Windows).

Проверка: в отдельной копии запретили встраивать `jf64_exp` ([cur2-noinline.patch](cur2-noinline.patch)). A/B той же методикой:

| Машина | Документ | исправленная / новая | пар, где исправленная быстрее |
|---|---|---:|---:|
| Windows | `canada.json` | 0,917 | 15 из 15 |
| Windows | `marine_ik.json` | 1,009 | 11 из 15 |
| Windows | `large_50k.json` | 0,993 | 9 из 15 |
| Linux | `canada.json` | 0,990 | 15 из 15 |
| Linux | `large_50k.json` | 1,007 | 2 из 15 |

Против старой версии исправленная на Windows даёт для `canada.json` 1,004 (7 из 15). На Linux она дала +0,7% на `large_50k.json`, где вообще нет float, то есть это тоже эффект раскладки кода.

### Итоговая проверка исправления

Исправление внесено в `include/json_f64_fmt.h`. Сборка с ним: SHA-256 `a5821dc4…` (Windows), `c1e02733…` (Linux).

- **Проверки.** `tests/check_dumps_orjson.py` и `tests/check_dumps.py` прошли на обеих машинах, на AVX2 и на переносимом пути. Расхождений с orjson ноль.
- **Раскладка кода.** `rec_list` теперь 1045 инструкций, `rec_value` — 1477. Это меньше, чем в старой версии (1089 и 1531): там встраивалась прежняя запись экспоненты.

A/B старой версии `d744abe` против исправленной, 15 пар на документ, той же методикой ([ab-win32-base-fix.json](windows/ab-win32-base-fix.json), [ab-linux-base-fix.json](linux/ab-linux-base-fix.json)):

| Документ | Windows: исправленная / старая | пар, где быстрее | Linux: исправленная / старая | пар, где быстрее |
|---|---:|---:|---:|---:|
| `atlas.json` | 1,000 | 9 из 15 | 1,003 | 5 из 15 |
| `numbers.json` | 1,039 | 9 из 15 | 0,995 | 13 из 15 |
| `twitter.json` | 0,992 | 9 из 15 | 1,009 | 3 из 15 |
| `citm_catalog.json` | 0,839 | 9 из 15 | 1,009 | 4 из 15 |
| `canada.json` | 0,999 | 7 из 15 | 1,003 | 5 из 15 |
| `marine_ik.json` | 0,991 | 9 из 15 | 1,001 | 8 из 15 |
| `large_50k.json` | 0,994 | 11 из 15 | 0,994 | 5 из 15 |

На Windows замедление `canada.json` ушло. Цифры по `numbers.json` и `citm_catalog.json` (1,039 и 0,839) объясняются двумя уровнями времени одного процесса: исправленная версия выиграла 9 пар из 15 на обоих документах. На Linux все отличия в пределах ±1%. Самые устойчивые — `twitter.json` и `citm_catalog.json`, +0,9%: исправленная выиграла только 3 и 4 пары из 15. Это небольшая плата за −8% на `canada.json` под Windows.

**Linux и один результат.** На Windows oxjson при записи занимает меньше orjson почти везде; исключение — `citm_catalog.json` при шести результатах. На Linux в режиме «один» oxjson выше на 5 документах из 7, сильнее всего на `large_50k.json`: 8,68 против 4,70 МиБ.

Около 4 МиБ — это освобождённый рабочий буфер oxjson, который glibc не вернул системе. Утечкой это не является: в режиме «шесть» память переиспользуется, и oxjson там не выше orjson. Но разовый прирост RSS на Linux у oxjson выше.
