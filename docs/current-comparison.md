# Текущая oxjson 0.4.1 против orjson 3.13.0 — 29 октября 2026

Локальная сборка из рабочей копии: **oxjson 0.4.1**, build revision 4, `prod`; **orjson 3.13.0**, **CPython 3.11.4**, Windows AMD64, AMD Ryzen 9 5900X. Это сравнение текущей сборки в одинаковой среде. Старые таблицы 0.4.0 и другой Python не являются базой для расчёта регрессии между релизами. Нового прогона на Linux в этой проверке нет.

Исходники замеренной сборки совпадают с коммитом `d744abe` (хеши в [current-build-20261029.json](../bench/results/current-build-20261029.json)). Следующий коммит `a3697b3` изменил запись float в `dumps` под формат orjson; разбор (`loads`) он не трогает. Цифры `dumps` ниже относятся к сборке до этого изменения. 30 октября запись перемерили на обеих версиях на этой машине и на Linux ([отчёт](../bench/results/dumps-remeasure-20261030/report.md)). Память записи не изменилась. Скорость не изменилась везде, кроме `canada.json` на Windows: там новая версия была на 8–9% медленнее из-за раскладки кода у gcc 15. Следующее исправление вернуло её к уровню старой версии. На Linux при записи с одним удерживаемым результатом oxjson занимает больше RSS, чем orjson, на 5 документах из 7: glibc не возвращает системе освобождённый рабочий буфер.

## Скорость

[Исходные повторы](../bench/results/speed-current-20261029.json): семь документов, семь независимых процессов для каждой библиотеки и документа, всего 98 процессов. Каждый процесс делает прогрев и усредняет три серии по десять вызовов; ниже медиана процессных средних и диапазон минимум–максимум. GC включён; освобождение результата находится за пределами таймера вызова. Порядок библиотек чередуется между повторами. Собственные нагрузочные тесты памяти завершены до этих замеров; внешние фоновые задачи не контролировались. Привязка к одному ядру не задавалась.

В 11 из 14 сценариев медиана времени oxjson меньше. Проигрыши: `atlas.json dumps` — на 12.3% больше времени; `citm_catalog.json dumps` — на 18.7% больше времени; `large_50k.json dumps` — на 10.9% больше времени. ## Память с удержанием результатов

[Расширенная матрица](../bench/results/memory-current-20261029.json): семь документов, две библиотеки, семь сценариев и пять свежих процессов на сочетание — 490 процессов. Каждый включает десять раундов по двадцать вызовов после прогрева. Отдельно выполнены 147 процессов переносимого пути и 16 процессов адресных серий: **653 запуска** всего. Десять самопроверок измерителя прошли, включая реальное выделение с записью по страницам, скрытый нулевым приростом пика буфер, неполный ответ и промежуточный всплеск с последующим спадом.

Ниже прирост **private commit процесса**, МиБ (2**20 байт), медиана [мин–макс] пяти процессов. «Один» — `held - baseline`; «шесть» — `held_many - released` для пакета из шести одновременно удерживаемых результатов после первого вызова и его освобождения. В частности, `canada dumps` в этой среде требует меньшего прироста private commit у oxjson. Прежний противоположный результат был получен с orjson 3.10.12 и более ранним измерителем: он не описывает сравнение с 3.13.0. `large_50k loads`: три процесса на библиотеку, 30 раундов по 30 вызовов. У oxjson один повтор остался на исходном уровне, в одном был подъём примерно на 1 МиБ с последующим спадом, в одном — подъём примерно на 1 МиБ с дальнейшим плато. Повторяющегося прироста на каждом раунде в этой серии не видно; причина ступени не установлена. `canada dumps`: пять процессов на библиотеку, 30 раундов по 100 вызовов; наблюдённый рост после прогрева — 0 МиБ у обеих библиотек. Это конечные серии по числу вызовов, а не 30-минутный тест.

Отсутствие превышения порога — результат регрессионной проверки, а не доказательство отсутствия любых утечек. Точки на границах раундов не фиксируют все временные пики. В [методике](memory-testing.md) описаны ограничения private commit/RSS и исторических пиков процесса.

## Корректность и проверка документации

В текущем окружении основной и переносимый пути прошли каждый: 229 файлов, 30 000 случайных документов, проверки блоков Python, памяти процесса и ссылок, 46 330 сравнений `dumps` с orjson (numpy 2.4.6). Сравнение 160 случаев AVX2/portable дало одинаковые хеши. Эти проверки не означают полного покрытия всех типов, входов и вариантов флагов.

Примеры обоих README проверены: `loads` для bytes/bytearray/memoryview/str, сериализация примера, сортировка и отступы, бинарные `load`/`dump`, тип и позиция ошибки, `allow_nan=False`, значения экспортированных `OPT_*` и версия из pyproject.toml. Строки старых коэффициентов памяти удалены, исторические версии подписаны, «все тесты» заменено на фактически запускаемые стандартные проверки, отсутствие утечек не объявляется гарантией. Таблица платформ описывает конфигурацию сборки, а не подтверждение всех опубликованных wheels.

## Воспроизведение и происхождение сборки

[Хеши исходников, компилятор и флаги](../bench/results/current-build-20261029.json), [изменения исходников относительно HEAD](../bench/results/current-source-20261029.patch). SHA-256 загруженных расширений и входов указан в каждом новом JSON; проверено совпадение между скоростью и всеми сериями памяти.

Windows, из корня проекта:

```powershell
python -m venv build/current-audit-env
& ./build/current-audit-env/Scripts/python.exe -m pip install orjson==3.13.0 numpy==2.4.6
& ./build/current-audit-env/Scripts/python.exe make_ext.py
& ./build/current-audit-env/Scripts/python.exe tests/check_memory_measurements.py
& ./build/current-audit-env/Scripts/python.exe bench/current_compare.py --repeats 7 --output bench/results/speed-current-20261029.json
```

Точные команды каждой серии памяти, включая список семи файлов, `--portable`, `--repeats`, `--rounds`, `--calls` и `--retain`, сохранены в поле `command` соответствующего JSON. Замеры скорости следует запускать после завершения остальных нагрузочных тестов. Для проверки корректности выполнены `tests/check_versions.py`, `tests/check_dumps_orjson.py` на обоих путях и `tests/check_portable.py`; полный `tests/run_all.py` в этой сессии не запускался. Публичные conformance-наборы и длительная кампания фаззинга заново не прогонялись.
