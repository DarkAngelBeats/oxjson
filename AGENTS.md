# Правила изменений oxjson

- Перед изменением зафиксируй ожидаемое поведение и способ его проверки.
- Исправление ошибки начинай с воспроизводимого входа и проверки, которая падает
  по ожидаемой причине. Сохраняй совместимость публичного API и документированные
  отличия от orjson, включая типы, точность чисел и обработку ошибок.
- Изменения ядра проверяй на AVX2 и переносимом пути. Подбирай проверки из
  `tests/check_versions.py`, `tests/check_dumps_orjson.py`, `tests/check_loads.py`,
  `tests/check_dumps.py` и `tests/check_portable.py` по затронутому поведению.
  Для сборки и полного прогона используй `python tests/run_all.py`.
- Проверка с расхождениями, падением или пустым ответом дочернего процесса
  должна возвращать ненулевой код завершения; одного сообщения FAIL недостаточно.
- Оптимизацию принимай только после проверки корректности и измеренного выигрыша
  относительно исходной версии. Сравнивай обе сборки на одной машине, одном
  Python, одинаковых входах и настройках GC; повторяй серии и учитывай разброс.
- Записывай версии или хеши сборок, команды, входы, число повторов, время,
  память и исходные результаты. Для сравнения с orjson используй ту же среду.
  Не объявляй выигрыш, если он сопоставим с шумом или измерений нет.
- Проверяй соседние сценарии: ускорение одного файла не должно скрывать
  регрессию других. Явный компромисс скорости и корректности/ресурсов описывай.
- Общий исходник, собранный для разных платформ, публичный API, таблица
  генератора или запасной путь не являются мёртвым кодом из-за отсутствия
  прямого вызова в одном файле. Перед удалением проследи сборку и ссылки.
- Не дроби горячие функции и не объединяй специализированные пути только ради
  метрик сложности или устранения похожих строк; подтверждай пользу проверками.
